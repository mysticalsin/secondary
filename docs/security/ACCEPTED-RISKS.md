# Accepted risks

Findings from the B2 and B3 security reviews that are not fixed in code, with the reason, the owner and when to look again. An item here is a decision, not an oversight. Anything that is fixed is in `_relay/HANDOFF.md` with its test.

Owner for every row: Tony Walteur (sponsor and platform owner), until a named security owner exists.

| ID | What stays | Why it is acceptable now | Condition that ends the acceptance | Review by |
|---|---|---|---|---|
| I-02 | `groupMapSet` (Entra group to role) has no admin route, so the mapping cannot be edited in a deployed environment. | It is a missing feature, not an exposure. Mapped roles can never be admin roles (`PRIVILEGED_ROLES`, M-11), and nobody can add a mapping without database access. A two-person route needs a new change kind, its UI and tests. | The first tenant that signs in with Entra groups. Build it as a governance change kind so it keeps the two-person rule. | Before the staging pilot with real Entra groups |
| I-04 | Staging and prod MCP have empty Access settings, so `/authorize` fails closed and MCP is unusable there. | It fails closed. Nothing is exposed. | Before MCP is piloted in staging: set `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` for the MCP worker (see `docs/runbooks/ENTRA-SETUP.md`). | Before the staging pilot |
| M-03 (source bodies) | Synced SharePoint bodies stay in the workspace objects when a person is erased. | They are the company's mirror of files held at the source, not the person's own data. Erasing them from the mirror would be undone by the next sync. The right place to erase them is the source; the connector then removes them (delete and purge propagate, see the connector tests). Wiki facts derived from a source are forgotten when the source goes (B3 M-02), and the person's own text, comments and Personal Brain are pseudonymised or wiped. | A request to erase text that sits inside a mirrored file and cannot be removed at the source. | Next DPIA review |
| M-03 (audit walk size) | One erase pages through at most 800 audit pages of 500 receipts (400 000 receipts) in a single request. | The walk is idempotent and runs first, so a tenant above that size gets a clean 502 and nothing half-erased. Pilot tenants are far below it. | A tenant with more than about 100 000 receipts. Persist the audit cursor in the erase request and resume it. | When any tenant passes 100 000 receipts |
| M-03 (tombstones) | An erasure leaves a tombstone (principal id, pseudonym, the person's address as typed) in the tenant's own object for 90 days. | It is needed to undo a restore of an older backup, and 90 days is twice the 35 day backup retention. It is never exported, never backed up, and is not readable through any route. It lapses by itself and the retention job drops it. | A longer backup retention. `TOMBSTONE_DAYS` in `workers/api/src/ops-rights.ts` must stay above `BACKUP_RETENTION_DAYS`. | When backup retention changes |
| M-03 (ACL cache after key rotation) | After `CONNECTOR_HMAC_KEY` is rotated, cached read decisions written under the old key stay in the connector until the item changes. | The rows are keyed by an HMAC, so they cannot be mapped to a person without the old key, and they never grant access (each is a yes or no that expires after 15 minutes). | Rotation of the connector key during an erasure request: run the erase again after the rotation. | n/a |
| I-05 (scope list) | `GET /v1/admin/scopes` and the change views still show an NDA account's name to configure holders who hold no named grant. Inbox titles no longer do. | Administering a named NDA grant needs to name the account. The labels are names, never content, and only configure holders and the stewards of that scope see them. | A requirement that admins administer NDA accounts by id only. | Next governance review |
| M-08 (dev) | In the deployed dev environment any Access user may send `X-Demo-Persona`. | The data is synthetic and the Access policy admits a named group. One address under several personas counts as one person for every two-person rule: governance changes, content release and review, wiki decisions, the prod switch re-enable, rights export and erase, and the ops restore (N-01, matched on the Entra subject or the normalised address, in the tenant's own object). A tester cannot approve their own change by switching persona. The one exception is a local run on loopback, where each persona gets its own plus-address by design, so a local test pass says nothing about a second human. | Never run `ENVIRONMENT=dev` for a pilot. Staging and prod ignore the header. | Before any pilot |
